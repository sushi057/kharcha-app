# Task 7 report: rule-based categorization and idempotent re-parse

## Matching algorithm (`Categorizer`)

`Categorizer(rules: List<RuleEntity>)` sorts the rules by `priority` descending
once at construction time. `categorize(remark, merchant)` picks the haystack
(`merchant` if non-null, else `remark`) and walks the sorted rules, returning
the `categoryId` of the first rule whose `matchPattern` matches:
`matchesPrefix = true` -> `haystack.startsWith(pattern, ignoreCase = true)`;
`false` -> `haystack.contains(pattern, ignoreCase = true)`. Returns `null` if
no rule matches. Because patterns are matched as substrings/prefixes of the
(possibly truncated) haystack rather than the reverse, a merchant name cut
off mid-word by the 160-char SMS limit (e.g. `...RESTAU`) still matches a
full pattern like `HANKOOK SARANG` as long as the pattern itself is fully
present before the truncation point.

## Re-parse: preserving overrides and staying idempotent (`ReparseService`)

`ReparseService(rawMessageDao, transactionDao, ruleset, categorizer)` has one
method, `reparseAll()`. For every non-ignored `RawMessage`:

1. Look up any existing transaction for that raw message via the new
   `TransactionDao.getByRawMessageId(rawMessageId)` query.
2. **If that transaction exists and `categoryIsManualOverride == true`, skip
   it entirely** — no re-parse, no category recompute, nothing touched. This
   is the override-preservation guarantee.
3. Otherwise, re-run `ruleset.parse(raw.body)`:
   - `Parsed` -> recompute `categoryId` via `categorizer.categorize(remark,
     merchant)`, then either `insert` a new `TransactionEntity` (first time
     seeing this raw message) or `update` the existing row in place, setting
     only `categoryId` (all other fields — including any
     `excludedFromSpending`/`isManualEntry` the user set — are carried over
     unchanged via `.copy()`).
   - `Ignored`/`Unrecognized` -> leave any existing transaction alone.

Idempotency comes from step 1's `rawMessageId` lookup: each raw message maps
to at most one transaction, so a second (or Nth) `reparseAll()` call updates
the same row instead of inserting a duplicate. The `ReparseTest` calls
`reparseAll()` twice in a row after the manual override and asserts exactly
one transaction row exists and its category/override flag are unchanged.

Added two DAO methods needed for this (not schema changes — no new tables or
columns, just queries):
- `RawMessageDao.getAll(): List<RawMessage>`
- `TransactionDao.getByRawMessageId(rawMessageId: Long): TransactionEntity?`

No Room schema version bump was needed; `data/schemas/com.kharcha.data.KharchaDatabase/1.json`
is unchanged.

  should reuse `Categorizer`/`ReparseService`'s pattern — i.e. an inserted
  `RawMessage` should get its `TransactionEntity` created with
  `categoryIsManualOverride = false` initially, and `categoryId` set via
  `Categorizer.categorize(...)` at ingest time, not left null, so the two
  code paths (ingest-time categorize, and later reparse) agree. If Task 6
  already wrote its own insert logic independent of `ReparseService`, it's
  worth checking it doesn't duplicate the `rawMessageId` uniqueness
  assumption `ReparseService` relies on for idempotency.
- **Task 6 / `:app` wiring**: nobody currently calls
  `Room.databaseBuilder(...).addCallback(KharchaDatabase.seedCallback)` in
  application code — that's out of scope for `:data`, but whichever task
  constructs the real (non-test) `KharchaDatabase` in `:app` must attach
  `seedCallback` or the seed categories/rules will never be created for real
  users.
- **Task 11 (budgets/notifications)**: `CategoryEntity.isFee`/`isIncome`
  flags exist so spending aggregation can exclude fees/income from
  discretionary totals — worth confirming Task 11's budget math actually
  filters on those flags rather than re-deriving "is this spending" from
  `direction` alone (a `Charge` debit still needs excluding).
- **Rule editing UI (whichever task owns it)**: `Categorizer` is
  constructed once from a rules snapshot; if the UI lets a user add/edit
  rules and then wants them to apply retroactively, that flow should call
  `ReparseService.reparseAll()` with a freshly-loaded rule list, not rely on
  a stale `Categorizer` instance.

## Fix report: review follow-ups (priority tie-break determinism)

Code review flagged that priority ties were not deterministically resolved:
`Categorizer` used `sortedByDescending { priority }` (a stable sort, so ties
resolved to *caller-supplied list order*), while `RuleDao.observeAll()` was
`ORDER BY priority ASC` with no secondary sort column — SQLite gives no
ordering guarantee for ties absent an explicit tiebreak column, so two
equal-priority rules could flip winners depending on physical row order
(e.g. after a VACUUM or future migration).

Fix (both halves, as requested):
- `RuleDao.observeAll()` (`data/src/main/kotlin/com/kharcha/data/dao/RuleDao.kt:25`):
  changed `ORDER BY priority ASC` to `ORDER BY priority ASC, id ASC`.
- `Categorizer` (`data/src/main/kotlin/com/kharcha/data/Categorizer.kt:16`):
  changed `rules.sortedByDescending { it.priority }` to
  `rules.sortedWith(compareByDescending<RuleEntity> { it.priority }.thenBy { it.id })`
  — ties now resolve by ascending `id` regardless of the order the caller
  supplied the rule list in.

Also applied the Minor: added a doc comment above the `existing != null`
update branch in `ReparseService.kt` (`reparseAll`, around line 64) stating
that `reparseAll()` is a categorization-only refresh — it does not resync
`amountMinorUnits`/`remark`/`merchant`/etc. if a future parser change would
extract different values for an already-ingested raw message. Behavior is
unchanged; documentation only.

### Regression test

Added to `CategorizerTest.kt`:

```kotlin
@Test
fun `equal priority ties break deterministically by id regardless of supplied order`() {
    val ruleA = RuleEntity(id = 100, matchPattern = "cIPS", matchesPrefix = true, categoryId = fees, priority = 50)
    val ruleB = RuleEntity(id = 200, matchPattern = "Charge", matchesPrefix = false, categoryId = dining, priority = 50)

    val abOrder = Categorizer(listOf(ruleA, ruleB))
    val baOrder = Categorizer(listOf(ruleB, ruleA))

    val remark = "cIPS Fund Trf Charge"
    assertEquals(abOrder.categorize(remark, null), baOrder.categorize(remark, null))
    assertEquals(fees, abOrder.categorize(remark, null))
    assertEquals(fees, baOrder.categorize(remark, null))
}
```

Both rules match `"cIPS Fund Trf Charge"` (ruleA via `startsWith("cIPS")`,
ruleB via `contains("Charge")`) at equal priority 50; the test asserts the
winner (`fees`, the lower-id rule) is identical no matter which order the
list is constructed in. All prior assertions in the file are unchanged.
