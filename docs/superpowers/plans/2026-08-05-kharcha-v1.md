# Kharcha v1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** An Android app that reads Siddhartha Bank `SBL_Alert` SMS, parses them into categorized transactions, and visualizes spending — entirely on-device.

**Architecture:** Three Gradle modules. `:parser` is pure Kotlin (no Android) and turns an SMS body into a `ParseResult`. `:data` is Room persistence, keeping every raw SMS forever so history can be re-parsed. `:app` is the Compose UI plus ingestion (`BroadcastReceiver` → WorkManager, plus a one-time inbox backfill).

**Tech Stack:** Kotlin 2.x, Jetpack Compose (Material 3), Room, WorkManager, Hilt, kotlinx-datetime, JUnit5 + kotlin.test, Turbine, Robolectric, Gradle version catalog.

Spec: `docs/superpowers/specs/2026-08-05-kharcha-sms-expense-tracker-design.md`

## Global Constraints

- **Money is `Long` minor units.** Never `Double`, never `Float`, for any monetary value anywhere in the codebase. NPR 2,984.00 is `298400L`.
- **Currency is explicit** on every monetary value. `NPR` and `USD` both occur. Never assume.
- **`:parser` has zero Android dependencies.** It is a `kotlin("jvm")` module. If a task makes you add an Android dependency to `:parser`, the design is wrong — stop and flag it.
- **Parse failure is a value, never an exception, never a silent drop.** `ParseResult.Unrecognized`.
- **A partially-bad message is `Unrecognized`, not a guess.** If the amount or date inside an otherwise-matching message fails to parse, the whole message is `Unrecognized`.
- **Sender ID is `SBL_Alert`**, matched case-insensitively.
- **`minSdk = 26`**, `targetSdk = 35`, `compileSdk = 35`, JVM target 17.
- **Application ID:** `com.kharcha.app`. Module packages: `com.kharcha.parser`, `com.kharcha.data`, `com.kharcha.app`.
- **TDD.** Every task writes the failing test first, watches it fail, then implements. Commit at the end of every task.
- **UI constraints (from `impeccable`), apply to every UI task:**
  - Do NOT use Inter or a system default as the display font.
  - Do NOT use purple-to-blue gradients.
  - Do NOT nest cards inside cards.
  - Do NOT use gray text on colored backgrounds.
  - Do NOT use pure black or untinted gray — all neutrals carry a color bias.
  - Do NOT use bounce or elastic easing.
  - Do NOT put a rounded-square icon tile above every heading.

- [ ] **Step 3: Implement Family A**

One regex over the whole body:

```
^Dear\s+\w+,\s*AC\s+(?<account>\S+),\s*NPR\s+(?<amount>[\d,]+(?:\.\d{1,2})?)\s+(?<direction>withdrawn|deposited)\s+on\s+(?<date>\d{2}/\d{2}/\d{4})\s+(?<time>\d{2}:\d{2}:\d{2})\s+for\s+(?<remark>.+)$
```

Applied with `RegexOption.IGNORE_CASE` and `DOT_MATCHES_ALL` (remarks can wrap). Trim the remark. Date parsed as `dd/MM/yyyy HH:mm:ss`; a failed date or amount parse returns `Unrecognized`, not a partial transaction.

Merchant extraction: if the remark starts with `QR Payment to ` (case-insensitive), the merchant is the rest; otherwise merchant is null. `remarkTruncated` is true when the body length is at/near the 160-char SMS boundary and the remark ends without terminal punctuation — implement as `body.length >= 155 && !remark.endsWith('.')`.

- [ ] **Step 3: Implement**

Check the ignore patterns **first**, before any transaction pattern, so an OTP containing a currency amount can never be misread as a transaction. Ignore patterns: body contains `is your OTP` (case-insensitive), or matches `^Your purchase code at .* is \d+$`.

Then the card regex:

```
^SBL\s+Card\s+(?<card>\S+)\s+used\s+at\s+(?<merchant>.+?)\s+for\s+USD\s+(?<amount>[\d,]+\.\d{2})\s+on\s+(?<date>\d{2}\.\d{2}\.\d{2})\s+(?<time>\d{2}:\d{2})\s+Authid\s+(?<authid>\w+)(?:\s+Remaining\s+Balance\s+after\s+txn\s+USD\s+(?<balance>[\d,]+\.\d{2}))?
```

Date format is `dd.MM.yy HH:mm` — note this differs from Family A. Two-digit years map to 2000+. The balance group is optional; a missing balance yields `balanceAfter = null` and is not a parse failure. `remark` for card messages is the merchant descriptor.

Dispatch order inside `parse`: ignore list → Family A → Family B → `Unrecognized`.
